# 🚨 КРИТИЧЕСКИЕ ПРАВИЛА БЕЗОПАСНОСТИ ПРИ НАПИСАНИИ МОДУЛЕЙ (LOCKED BOOTLOADER / TEMP ROOT)

КОНТЕКСТ УСТРОЙСТВА:
Устройство работает на базе Android (Vivo / iQOO / OriginOS) с ЗАБЛОКИРОВАННЫМ ЗАГРУЗЧИКОМ (`flash.locked=1`) и ВРЕМЕННЫМ РУТОМ (Temp Root / эксплойт ядра), который ПОЛНОСТЬЮ СЛЕТАЕТ ПОСЛЕ КАЖДОЙ ПЕРЕЗАГРУЗКИ.
Любое постоянное изменение в разделе /data, которое требует наличия смонтированного модуля при загрузке, УБЬЕТ СИСТЕМУ В БУТЛУП, из которого невозможно выйти без полного сброса данных (Wipe Data).

---

## ❌ ЧТО КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО ДЕЛАТЬ В МОДУЛЯХ И СКРИПТАХ (service.sh, post-fs-data.sh, customize.sh)

### 1. ЗАПРЕТ НА pm disable, pm hide И pm uninstall ДЛЯ СИСТЕМНЫХ КОМПОНЕНТОВ
* Никогда не отключать через `pm` или `cmd package` базовые системные пакеты, отвечающие за запуск и работу фреймворка:
  * com.android.packageinstaller / com.google.android.packageinstaller / com.vivo.appfilter (Установщики пакетов — при их отключении и слете темпового рута SystemServer падает с фатальной ошибкой getRequiredInstaller() при старте).
  * com.android.systemui, com.android.settings, com.android.providers.*, com.android.phone, com.android.bluetooth.
  * Системные сервисы оболочки (com.bbk.*, com.vivo.*, com.iqoo.*), от которых зависит загрузка рабочего стола и проверки безопасности.
* Почему: Команды pm записывают состояние в /data/system/users/0/package-restrictions.xml. Этот файл не очищается при перезагрузке, когда слетает темповый рут, и не сбрасывается в Safe Mode.

### 2. ЗАПРЕТ НА ПОДМЕНУ ПРИВИЛЕГИРОВАННЫХ ПРИЛОЖЕНИЙ (/system/priv-app) С ОТКЛЮЧЕНИЕМ ОРИГИНАЛА
* Нельзя монтировать кастомный APK в /system/priv-app или /product/priv-app с одновременным отключением стокового аналога.
* Если модуль заменяет системный компонент через Magic Mount / OverlayFS, оригинальный системный пакет должен оставаться включенным (`enabled`) в системе как резервный вариант на случай загрузки без рута.

### 3. ЗАПРЕТ НА МОДИФИКАЦИЮ post-fs-data.sh И РАННИХ СТАДИЙ ЗАГРУЗКИ
* На темповом руте рут-права и монтирование появляются уже после старта системы, но если модуль оставит скрипты в /data/adb/post-fs-data.d/ или сломает права доступа (SELinux-контексты) в /data/system/, система не сможет пройти инициализацию.
* Не менять права (chmod / chown) и контексты (chcon) на системных директориях внутри /data/system/, /data/misc/ и /data/property/.

### 4. ЗАПРЕТ НА ПРЯМУЮ ЗАПИСЬ В ФИЗИЧЕСКИЕ РАЗДЕЛЫ (dd, blkdiscard)
* Строго запрещены любые команды записи в блочные устройства (/dev/block/by-name/*):
  * Не трогать boot, init_boot, vendor_boot, recovery, vbmeta, dtbo, super, persist, metadata.
* На заблокированном загрузчике нарушение контрольной суммы vbmeta или обоих слотов (_a и _b) приводит к глухому Red State без возможности зайти даже в стоковое рекавери.

### 5. ЗАПРЕТ НА ПОСТОЯННЫЕ settings put global/secure/system, ЛОМАЮЩИЕ ЗАГРУЗКУ
* Не записывать через settings put экспериментальные флаги в global или secure (например, подмену verifier_verify_adb_installs, hidden_api_policy, системных провайдеров или кастомных AccessibilityService), если нет уверенности, что система загрузится с ними без рута.

## ✅ КАК ПИСАТЬ БЕЗОПАСНЫЕ МОДУЛИ ДЛЯ TEMP ROOT (ПРАВИЛЬНЫЙ ПОДХОД)
1. Принцип «Нулевого следа после ребута»:
   Любое действие модуля должно работать только в оперативной памяти (ОЗУ / bind-mount / runtime-хуки) в рамках текущей сессии. После перезагрузки телефон должен загружаться как 100% чистый сток.
2. Временное перекрытие вместо отключения:
   Если нужно заменить системный APK, используйте только чистое перекрытие (replace / overlay) поверх включенного стокового пакета без вызова pm disable.
3. Защита от зависаний в `service.sh`:
   Любой скрипт в service.sh обязан иметь проверку на полную загрузку системы (while [ "$(getprop sys.boot_completed)" != "1" ]; do sleep 2; done) и не должен содержать бесконечных циклов без таймаутов.
4. Приоритет User-space решений (Shizuku / ADB):
   Всё, что можно сделать без рута (установка APK через InstallerX + Shizuku, заморозка обычных пользовательских приложений), должно делаться без модификации системных разделов.
